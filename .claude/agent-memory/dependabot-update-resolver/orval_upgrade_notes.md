`packages/frontend/orval.config.ts` は fetch client + mode: single + MSW mock生成を使う構成。zodは使用していない(依存にzodなし、`output.override.zod`未使用)ため、orval 8.18/8.19で導入された「Zod v4がデフォルト」という変更はこのリポジトリには影響しない。

orval v7 → v8 (8.19.0時点で確認)で `output.mock` の設定スキーマが破壊的に変更されている。
- 旧: `mock: { type: "msw", delay: 0 }`
- 新: `mock: { generators: [{ type: "msw", delay: 0 }] }`
旧形式のままだと `pnpm run openapi:update` (= `orval --config orval.config.ts`) が `TypeError: mock.generators must be an array of generator entries` で失敗する。

**Why:** orval 8.xでmockジェネレータが複数種類(msw, faker等)を同時出力できるようマルチジェネレータ構成に変更されたため。

**How to apply:** orvalをメジャーアップデートするPRを扱う際は、まず `pnpm --filter @tasche/frontend run openapi:update` を実際に実行してエラーが出ないか確認する。エラーが出たらorval公式ドキュメント(orval.dev/docs/reference/configuration/output)のmock/output設定を確認し、config側を新スキーマに追従させる。生成後は `MockHandler` で終わる関数が `src/api/generated/client.ts` 内に引き続きインライン生成されていること(`src/mocks/handlers/generated.ts` がこれをスキャンして`RequestHandler`を収集する仕組みに依存している)を確認する。

生成後の差分は多くの場合、単純なユニオン型(`number | null`等)を別ファイルに切り出す代わりにインライン化する、JSDocコメントの整形、`value.toString()` → `String(value)` のような軽微な最適化などで、実害のない差分になることが多い(2026-07にorval 7.18.0→8.19.0で確認)。差分を精査する際は `model/index.ts` のexport増減(ファイル削除)がsrcの他の場所から直接import されていないかを必ずgrepで確認すること。

**orvalのpatchバージョン更新(例: 8.19.0→8.20.0)の場合**、CIの`frontend-openapi`ジョブ(`git status --porcelain -- packages/frontend/src/api/generated` で差分を検知して失敗させる仕組み)は、生成ファイル先頭の `Generated by orval vX.Y.Z` というバージョンコメントが変わるだけでほぼ確実に失敗する(PR #79で確認、8.19.0→8.20.0、61ファイル全てで1行のみの差分。PR #90でも8.20.0→8.21.0で再現、同じく61ファイル全てで1行のみの差分。PR #111でも8.23.0→8.24.0で再現)。これはorval自体やAPI定義の破壊的変更ではなく、単に「コミット済みの生成物のバージョン表記が古い」というだけなので、`pnpm --filter @tasche/frontend openapi:update` を実行して再コミットすれば解決する。orvalのマイナー/パッチ更新PRでこのジョブが落ちていたら、まずこのケースを疑って良い。この再生成コミットは[[biome_schema_version_mismatch]]の$schema更新コミットとは分けて、それぞれ独立したコミットにするのがこのリポジトリの慣例(PR #79, #90, #111共通)。

**orval 8.24.0（PR #111、8.23.0→8.24.0）で「Drop version from default generated header」という変更が入り、生成ヘッダーのコメントが `Generated by orval vX.Y.Z 🍺` から `Generated by orval 🍺` に変わり、バージョン番号自体が埋め込まれなくなった。** これにより8.24.0以降のorval patch/minor更新では、上記の「バージョンコメントだけの差分」パターンは原則発生しなくなる見込み（ヘッダーが固定文字列になったため）。ただしAPI定義側の変更や生成ロジックの変更による実質的な差分は引き続き起こりうるので、`openapi:update`実行後は`git diff --stat`で差分の中身（1行×61ファイルの機械的な差分か、それ以外の実質的な変更か）を必ず確認すること。

**orval 8.21.0のリリースノートに「fix(security): escape spec-controlled strings in generated template literals and object keys」というセキュリティ修正が含まれていたことがある**(PR #90、8.20.0→8.21.0)。OpenAPI spec内の文字列がテンプレートリテラルやオブジェクトキーとして生成コードに埋め込まれる際のエスケープ漏れ(コード生成時のインジェクション)を修正するもの。このリポジトリの`openapi.json`には該当する特殊文字を含む値がなかったため、`openapi:update`実行後の差分はバージョンコメントのみで実害はなかった。ただしorvalのpatch更新でセキュリティ修正が含まれる場合があるため、リリースノートは必ず確認すること。

**orval 8.23.0（PR #100、8.21.0→8.23.0）で「Request option type inference from mutator」という変更が入り、`client.ts`内の全関数シグネチャで `options?: RequestInit` が `options?: Parameters<typeof authFetch>[1]` に変わった**（バージョンコメント以外で実質的な差分が出た初めてのケース）。`src/auth/authFetch.ts`の`authFetch<T>(url: string, options?: RequestInit)`の第2引数はRequestInitのままなので型としては等価であり、mutator（カスタムfetch関数）の実際の引数型から推論する方が正確、という改善。実害はなく型もそのまま通る。orvalのpatch更新でも`client.ts`にバージョンコメント以外の差分が出ることがある点に注意（従来は61ファイル全て1行のみの差分だったが、PR #100では`client.ts`だけ22箇所の型シグネチャ変更があった）。

**orval 8.26.0（PR #114、8.24.0→8.26.0）で「fix(fetch): spread Headers instance correctly when merging custom headers」というバグ修正が入り、body付きリクエスト（POST/PUT/PATCH/DELETE）を生成する各関数内で `headers: { 'Content-Type': 'application/json', ...options?.headers }` が、`options?.headers` が `Headers` インスタンスや `[string, string][]` 配列であってもエントリを正しく展開できる `getHeaders()` ヘルパー経由に変わった。従来の単純なオブジェクトスプレッドでは `Headers` インスタンスを渡した場合エントリが展開されずカスタムヘッダーが消える不具合があったための修正（正当なバグ修正で退行ではない）。`client.ts` のみ80行程度の実質的な差分になる（バージョンコメントだけの差分ではない）。このリポジトリでは生成関数の呼び出し元（`TasksPage.tsx`, `GoalWizard.tsx`等）がいずれも`options`引数（第2引数のheaders等）を渡していないため実害はゼロだった。orvalのpatch更新でも`client.ts`に実質的な差分が出ることがある点、引き続き注意（PR #100に続き2例目）。

**orval 8.28.1で「feat(core)!: de-inline mocks by default in single and tags modes」という破壊的変更（`!`付き）が入り、`mode: "single"` でも `output.mock.generators` で指定したモック（msw等）が既定でメインの `client.ts` にインライン生成されなくなり、別ファイル `client.msw.ts`（`.faker.ts`も同様）に分離されるようになった（PR #120、8.26.0→8.31.0で発覚。8.27.0〜8.31.0のどこかで導入）。このリポジトリでは `src/mocks/handlers/generated.ts` が `client.ts` のexportを走査して名前が`MockHandler`で終わる関数をMSWハンドラとして収集する実装になっているため、この変更をそのまま受け入れると `client.ts` からMockHandler関数が消え、MSWモックが全て無効になる（`pnpm test`は依存先コンポーネントのモックが空になり失敗する）。

**対処**: orvalが新設した `output.mock.inline: true` オプション（デフォルト`false`）を`orval.config.ts`に追加することで、従来通り`client.ts`にインライン生成される挙動を維持できる（`client.msw.ts`は生成されなくなる）。既存のモック走査アーキテクチャ（`generated.ts`）を変更せずに済む最小差分の修正。`client.msw.ts`を新たにコミットしてモック走査ロジックを2ファイル対応に変更する方法も可能だが、変更範囲が大きくなるため今回は見送った。

**Why:** orvalは`split`/`tags-split`モードでは元々ファイル分離だったが、`single`/`tags`モードでは長年インライン生成がデフォルトだった。8.28.1でモックコード（特にfakerの大量のダミーデータ生成コード）を実装コードから分離し、プロダクションビルドに影響しない構成へ統一する意図の変更（`inline`オプション自体は8.28.1で新設）。

**How to apply:** orvalをアップデートするPRで`pnpm openapi:update`実行後に `client.msw.ts`（または`.faker.ts`）が新規のuntrackedファイルとして生成された場合、このパターンを疑う。このリポジトリのように`client.ts`側のMockHandlerインライン生成に依存した仕組みがある場合は`orval.config.ts`の`output.mock`に`inline: true`を追加して再度`openapi:update`を実行し、`client.msw.ts`が生成されず`client.ts`にMockHandler関数（`grep -c MockHandler client.ts`で件数確認、更新前と同数なら復元成功）が復元されることを確認する。
